## 一、最终方案（v3.3 的设计）

### 1. 数据链路（安全中间层）

```
遥控器 teleop ──>/teleop_cmd_vel──>【safety_stop】──>/cmd_vel──> 底盘
                                        ↑
                                    /scan（雷达）
```

遥控器改道，让避障节点成为"中间层"，这样它能在指令到达底盘前拦截/限速：

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r cmd_vel:=/teleop_cmd_vel
```

### 2. 核心算法：碰撞预测 + 速度限幅（不是开关）

```python
允许最大前进速度 = (前方最近距离 − 安全余量) / 反应时间
实际输出速度    = min(遥控期望速度, 允许最大前进速度)
```

| 参数 | 取值 | 依据 |
|---|---|---|
| `SAFETY_MARGIN` | 0.10 m | 雷达安装点到车头前缘的距离 |
| `REACTION_TIME` | 0.70 s | **实测雷达 2 Hz（0.5 s/帧）+ 通信制动延迟 0.2 s** |
| `HARD_STOP_DISTANCE` | 0.12 m | 真兜底，小于它才完全不动 |
| `FRONT_HALF_ANGLE` | ±60° | 正前方扇区 |
| 控制频率 | 20 Hz | 必须远高于雷达 2 Hz，才能在两帧之间持续压制速度 |

示例：距离 0.5 m → 允许 0.57 m/s；0.3 m → 0.29 m/s；0.2 m → 0.14 m/s；< 0.12 m → 0。

### 3. 三条永远放行

| 放行项 | 理由 |
|---|---|
| 转向 `angular.z` | 狭小空间靠转向脱困，不会因转向撞前方 |
| 倒车 `linear.x < 0` | 后退远离障碍，永远安全 |
| 零速 | 本来就不动 |

### 4. 三重 Fail-Safe

| 机制 | 触发条件 | 行为 |
|---|---|---|
| 近距盲区修复 | `0 < r < range_min`（RPLIDAR range_min=0.15 m） | 按 `range_min` 计入，**不丢弃** |
| 数据超时保护 | 1.5 s 未收到 `/scan` | 禁止前进（看不见就停车） |
| 空帧判定 | 扇区无有效点但整帧有数据 | 判定前方空旷（v3.3 修复） |

### 5. QoS 自适应（本机特有）

本机 `/scan` 发布者 `rplidar_composition` 使用 **RELIABLE**，而 `qos_profile_sensor_data` 是 **BEST_EFFORT** —— **不兼容，一条数据都收不到**。故同时建立两个订阅：

```python
QOS_RELIABLE = QoSProfile(depth=10, reliability=ReliabilityPolicy.RELIABLE)
self.create_subscription(LaserScan, '/scan', self.scan_callback, QOS_RELIABLE)
self.create_subscription(LaserScan, '/scan', self.scan_callback, qos_profile_sensor_data)
```

## 二、六版迭代全过程（报告核心素材）

| 版本 | 做法 | 实测问题 | 根因 | 修复 |
|---|---|---|---|---|
| **v1** | 前方 < 0.3 m → 全部指令清零 | ✅ 能停（0.290 m 停住）；❌ 狭小空间前进被禁死，只能人工拉车 | 状态封锁（一刀切），无迟滞 | → v2 |
| **v2** | 加迟滞（0.3 进 / 0.4 出）+ 被挡时放行倒车转向 | ✅ 可倒车脱困；❌ 进圈即前进速度为 0，无法缓慢蹭 | 仍是开关式，非连续调速 | → v3 |
| **v3** | 碰撞预测：`v_allow=(d-margin)/t`，转向倒车永久放行 | ❌ **直接撞上障碍** | **近距盲区**：`r < range_min` 的点被丢弃 → 最小距离变 `inf` → `v_allow=inf` → 保护完全失效 | → v3.1 |
| **v3.1** | 近距点按 `range_min` 计入 + 数据超时 + 空帧保护 | ❌ 一直刷 `雷达数据超时`，车不动 | **QoS 不兼容**：发布者 RELIABLE vs 订阅者 BEST_EFFORT（兼容矩阵 ❌ 格） | → v3.2 |
| **v3.2** | reliable + best_effort 双订阅自适应；日志改为状态切换打印 | ❌ 仍无数据 | **硬件**：journalctl 显示 `Can not start scan: 80008002` + 相机 `X_LINK_ERROR` 同时报错 → **电池仅 10%，USB 供电不足** | 充电 + 整机重启 |
| **v3.3** | 扇区空但整帧有效 → 判为前方空旷 | ✅ 全部正常 | 上一版空帧保护保留了旧距离 → 转弯后**永久限速** | ✅ 收官 |

### 四类根因（每一类都留下一套判据）

| 类别 | 表现 | 定位手段 |
|---|---|---|
| **算法缺陷** | 撞墙 / 永久限速 | 观察日志中的距离数字；`inf` 参与运算推演 |
| **DDS 配置** | 收不到数据 | `ros2 topic info /scan --verbose` 看端点 QoS |
| **QoS 兼容** | 端点在、数据无 | QoS 兼容矩阵（可靠/尽力）逐格比对 |
| **硬件供电** | 雷达与相机同时故障 | `journalctl -u turtlebot4` 看设备级错误码 |

> 关键结论：**ROS 话题"存在" ≠ 数据在流动**。安全系统必须用"数据超时"判断，而不是用 `ros2 topic list` 里话题是否存在来判断。

## 六、可继续改进的方向（有余力再做）

1. **方向性限速**：用左右两侧扇区分别限速（转弯时更精确）
2. **底盘 bump/hazard 兜底**：订阅 `/hazard_detection`，雷达看不见的低矮/黑色障碍用碰撞传感器兜底
3. **灯环提示**：故障时发布 `/cmd_lightring` 变红，而不是只刷日志
4. **参数化**：把 5 个阈值改成 ROS 参数（`declare_parameter`），现场可调
5. **低速优先**：给前进速度加硬上限（如 0.3 m/s），配合 2 Hz 雷达更安全
